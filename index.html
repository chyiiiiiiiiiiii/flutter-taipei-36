用靜態資料集測 code quality rubric（Meta-Evals）
7/23 起加入的 run-evals 是一套 skill 評分流程：把 skill 丟進隔離環境執行任務，再用 rubric 逐條打分。做法看下一頁。
深入一頁 · 官方的 AI evals 怎麼做

拿 skill 當單元測試 來跑tool/dart_skills_lint/evals/

① 兩層 rubric
{ "repo_criteria": ["evals/code_quality_rubric.json"], "evals": [{ "prompt": // 真實的使用者請求 "expected_chat_output": // agent 該回什麼 "expected_repo_state": // 可驗證的斷言陣列 "agent_config": // 用哪個 harness }] }
compilation_and_health
零語法錯誤、dart analyze --fatal-infos 乾淨、測試要過
effective_dart_and_idioms
Effective Dart；分支代數型別時要用 Dart 3 switch expression 與窮盡 pattern matching
cross_platform_compatibility
路徑走 package:path，不准寫死 C:\ 或 /usr/local/bin
directory_and_placement_hygiene
程式碼進 lib/、測試進 test/、腳本進 bin/；不留暫存檔
② run-evals 的執行流程
1
每個 eval 開一個隔離的 branch workspace。偵測到多 workspace 掛載就直接失敗 —— 明文禁止靜默退回共用目錄，因為會 git state bleed、跨 eval 汙染。
2
開 With-Skill subagent：讀 skill、照做任務。要比較時才另開 Baseline（同一個任務，但不給 skill）。
3
不准 commit。只交回 git diff ＋ dart format / analyze / test 的輸出。
4
LLM judge 拿合併後的 rubric逐條打 PASS / FAIL。失敗時強制寫出「期望什麼」對「實際看到什麼」。
5
產出 markdown artifact：判定理由 ＋ 原始 diff ＋ stdout 全部留存。
Meta-Evals（07-24）：用 test_data/ 底下 bad_code 與 ok_code 兩份靜態 fixture 反過來測 rubric 本身 —— 抓不抓得到反模式，以及會不會誤殺乾淨的程式碼。
刻意不評的東西：dart format 已經修得掉的排版瑣事、要跑好幾分鐘才生得出來的完整架構、範圍外的 skill。另有 dart test test/skills_evals_test.dart 在 CI 檢查所有 evals.json 的結構一致性。
